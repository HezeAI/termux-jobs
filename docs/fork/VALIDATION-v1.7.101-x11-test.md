# Частная v1.7.101-x11-test: проверка VirGL GPU INFO и Fedora

Дата: 2026-10-23. Новая проверочная сборка; публикация после проверки HezeAI.

## Исходное поведение и изменение

По скриншотам разработчика v1.7.100: Void glmark2 рисовал и проходил первые этапы,
Alpine glxgears показывал шестерёнки; GPU INFO в обоих падал BadMatch/X_GetImage.
Fedora: такое же падение GPU INFO и glmark2 exit250/read104 на первом этапе.
Отчёт Void показывал готовность за5310ms, backend=vulkan и запущенный стол.

Для VirGL в Alpine/Fedora/Void GPU INFO теперь использует EGL pbuffer в отдельном
Python-процессе и выводит настоящий GL_VENDOR/GL_RENDERER/GL_VERSION выбранного
Mesa-клиента. Вывод подписан EGL: успешный запрос не выдаётся за тест GLX.
EGL_PLATFORM=surfaceless применяется только к дочернему процессу; библиотечные
пути, выбранный драйвер и собственный vtest-сокет наследуются. Родительское
окружение не меняется. Таймаут20секунд/ошибка/краш дают понятную неуспешную
диагностику без повторного GLX-запроса и без остановки стола.

Только Fedora VirGL переключён с ANGLE GL на Vulkan. Соответствующий backend
проверяется в установщике и при оценке маркера готовности. Версии GL не завышаются.
Обработчики процессов, собственные сокеты, guardian и остановка не изменены.

CPU и Turnip+Zink этих систем сохраняют glxinfo/glmark2/glxgears и прежние переменные.
Другие окружения и варианты рендера не переходят на новый GPU INFO. Упакованные
Kali, Alpine Mesa и прежние JNI-библиотеки идентичны v1.7.100. Агентские сессии,
SSH, серверные настройки и установленные окружения в ходе проверки не изменялись.

Управляемая копия helper обновляется в выбранном home при следующем старте стола.
Проверено обновление старого собственного helper без перезаписи ярлыков;
пользовательские правки и symlink сохраняются по прежним правилам.

## Доказательства

- 48 JVM проверок: X11IntegrationTest35, WorkspaceDesktopGpuTest9,
  DesktopProcessAssetTest4; ошибок/падений нет.
- 32 разных Python проверки: GPU tools18 (финальный набор), VirGL6,
  private Alpine client6, session policy2. В том числе CPU/Turnip обходят EGL-ветку,
  EGL-child получает лишь локальное изменение платформы, выбранный socket/driver
  сохраняется, timeout/краш не дают успех, частично созданный EGL-контекст/поверхность
  освобождаются, собственные fork-процессы останавливаются независимо от соседнего.

  Alpine(GL), Fedora(Vulkan), Void(Vulkan): exit0, EGL1.5, renderer virgl/Adreno830.
- Три реальные изолированные пробы рисования с теми же backend: треугольник,
  чтение пикселя255,0,0,255, client arrays и VBO; exit0, GL error0.
- Shell syntax и git diff --check прошли. ARM64 build успешен, DEX audit:
  13552 определения,31 оставшийся тип с явными review notes.

Локальные доказательства: .verification/virgl-info-fix/{python.log,
gpu-tools-final.log,jvm-results.json,egl-info-results.json,render-results.json,

и repository-local cache; установленный rootfs читался без установки пакетов.

В Alpine GL-сервер всё ещё сообщает EGL_BAD_ACCESS при завершении контекста;
запрос и рисование завершаются успешно. Эта общая проблема очистки не объявляется
исправленной. В проверенных Fedora/Void Vulkan-пробах такого сообщения нет.

## Оставшаяся проверка разработчиком

После обновления остановить/запустить выбранный стол: GPU INFO в Alpine, Void,
Fedora; полный GPU/glmark2 в Fedora. Проверить остановку и повторный запуск.
CPU и Turnip+Zink можно кратко проверить как пользовательскую регрессию.

Полный GUI/GLX/glmark2 через новый APK и чистый другой телефон не проверены
изолированными тестами. Внутренний сбой GLX/X_GetImage этим обходом не исправлен
для произвольных других GLX-программ. На устройстве иного GPU совместимость ANGLE
Vulkan может отличаться; успешные проверки Adreno830 не доказывают её для всех.

## Дополнение: проверка разработчика после сборки

HezeAI подтвердил работу Alpine, Void и Fedora после v1.7.101.
Это пользовательская проверка на настроенном телефоне, не чистая установка.

Новая открытая проблема Debian VirGL: скриншот 2026-10-23 09:36 показывает
корневой фон X11 без панелей/значков XFCE. Отчёт этого запуска: backend=gl,
rendererConnected=true, desktopReady=false, desktopStartupTimedOut=true,
34246ms, последний шаг xfce-session. Наблюдался xfce4-session, затем ожидание
futex; запуск оконного менеджера не отмечен. Оба desktop/guardian exit=-1:
завершение не наблюдалось, это не доказательство падения.

Отчёт локализует задержку до готовности XFCE, но не устанавливает причину:
графический вызов, D-Bus и восстановление сеанса пока не разделены. Успех
изолированных EGL-проб не подтверждает запуск полного Debian XFCE.
Следующий минимальный шаг — сравнение Debian ANGLE GL/Vulkan с запуском XFCE
и проверка зависшего процесса, без изменения CPU/Turnip и остальных окружений.
Этот сценарий остаётся открытым перед публичным релизом.
