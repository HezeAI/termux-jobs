# Частная v1.7.102-x11-test: Debian, Arch и openSUSE VirGL

Дата: 2026-10-23. Проверочная сборка; публичный релиз ожидает проверки разработчиком.

## Основание и изменение

HezeAI подтвердил Alpine/Fedora/Void после v1.7.101. Последующие проверки:

- Debian: корневой фон X11, без панелей/значков; backend GL, desktopReady=false,
  timeout34246ms. Последний шаг xfce-session; окно менеджера не наблюдалось.
  По сообщению разработчика другие рендеры Debian работают.
- Arch: XFCE готов за6901ms. GPU INFO падает BadMatch/X_GetImage; glmark2
  завершается exit250/read104 на первом этапе. В журнале EGL_BAD_ACCESS.
- openSUSE: XFCE готов за8307ms; glmark2-es2 рисует и прошёл первый этап,
  GPU INFO падает BadMatch/X_GetImage. Полный балл теста не представлен.

GPU INFO через отдельный ограниченный по времени EGL-процесс расширен на эти
три VirGL-цели. Прочие ветки GPU INFO, сами программы GPU и механика обновления
управляемых ярлыков сохранены. Вывод подписан EGL; это обход падающего запроса
GLX, не исправление всех GLX-программ и не доказательство готовности XFCE.

Debian и Arch используют ANGLE Vulkan; Arch переведён с multi-clients на upstream
fork на соединение. Запуск, установщик и оценка готовности согласованы по backend.
Установка по-прежнему требует подтверждения и полного явного набора компонентов;
отсутствие нужных Vulkan-библиотек не выдаёт READY. Архивы/драйверы не менялись.

openSUSE сохраняет работающий ANGLE GL. Termux/Ubuntu и уже проверенные
Alpine/Fedora/Void сохраняют свои прежние настройки. CPU, Turnip+Zink и wrapper
не запускают VirGL-сервер и не попадают в новый запрос GPU INFO.

Причина зависания Debian до оконного менеджера ещё не установлена окончательно.
Смена backend — кандидат на исправление, который надо проверить полным запуском
XFCE. Успешная EGL-проба не закрывает эту проблему и не разрешает объявить все
рабочие столы проверенными на чистом телефоне.

## Проверки, ревью и логическая инспекция

- 41 Python проверка прошла: GPU tools18, VirGL7, Alpine client6,
  session policy2, Arch8. Проверены выбор backend и пакетного менеджера,
  отсутствие нужного backend, неполный драйвер, CPU/Turnip/wrapper без запуска
  VirGL, наследование библиотек и собственного socket, обновление helper,
  права/подмена/повреждение cache, сохранение правок пользователя.
- Для всех шести Linux-целей проверен отдельный fork-сервер и отмена с очисткой
  своего socket. Дочерние процессы остаются в группе guardian; остановка одной
  группы не останавливает соседнюю. Сам механизм завершения процессов не изменён.
- 48 JVM проверок прошли: X11IntegrationTest35, WorkspaceDesktopGpuTest9,
  DesktopProcessAssetTest4. Shell syntax и git diff --check прошли.
- Три настоящих запроса нового EGL-helper и три пробы рисования прошли:
  Debian/Arch Vulkan и openSUSE GL, Adreno830. Pixel255,0,0,255, client arrays,
  VBO, GL error0, exit0. Библиотеки установленного rootfs читались; запускались
  свои независимые процессы/socket с cache внутри репозитория.
- В Debian/Arch Vulkan-пробах EGL_BAD_ACCESS не наблюдался. В openSUSE GL
  сообщение при очистке остаётся, хотя клиенты завершаются успешно.
  Отсутствие графических ошибок всех приложений не заявляется.
- Логически прослежены выбор до запуска, подготовка нужного backend, отдельный
  server/socket, разветвление по renderer, запрос GPU INFO, отмена и остановка.
  Агентские чаты, SSH и установленные окружения не изменялись.

Доказательства: локальная .verification/virgl-remaining-fix/, python-final.log,
jvm-results.json, egl-info-results.json, render-results.json, build.log,
apk-audit.json. Старый Arch fixture не проверял stdin гостя: устаревшее ожидание
inline pacman заменено проверкой argv выбранного Arch. Реальные пакетные команды
отдельно выполняются в изолированном guest fixture набора VirGL.

## Минимальная проверка разработчиком

1. После обновления остановить и запустить Debian VirGL: дождаться панелей и
   значков, проверить GPU INFO и GPU. Если снова корневой фон — сохранить отчёт.
2. Arch: GPU INFO, полный GPU/glmark2, остановка и повторный запуск.
3. openSUSE: GPU INFO и отсутствие регрессии рабочего GPU/glmark2-es2.

Полные XFCE/GLX/glmark2 после обновления, чистая установка другого телефона,
другие GPU/версии Android не проверены изолированными пробами и JVM-тестами.
