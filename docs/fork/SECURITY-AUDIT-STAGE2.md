## Codex: политика и прямые инструменты

Цепочка: `WorkspaceStore.Session` → `WorkspaceController.editSession` →
`CodexSessionShell.approval/invocation` → `codex-chat.cjs.params/verify` и
`codex-control.js` (resume). В v2.1.2 `codexAccess="full"` и отсутствующее
`codexConfirmActions` дают `danger-full-access` / `never`. Это подтверждённая
настройка, а не обход механизма подтверждений.

Проверен настоящий **Codex CLI 0.166.0 app-server** без аккаунта, с локальным
синтетическим Responses-провайдером. В запросах запуска сервер подтвердил
`approvalPolicy=untrusted`, `sandbox.type=dangerFullAccess`.

| Действие | Отказ | Положительный контроль |
| --- | --- | --- |
| `exec_command`, запись вне проекта | `item/commandExecution/requestApproval`; маркер не создан | Отдельные native command/exec чтение и запись внутри/вне проекта успешны при полном доступе. Это не модельный approval-путь. |
| `apply_patch`, новый файл вне проекта | `item/fileChange/requestApproval`; файл не создан | Разрешение создаёт файл. |
| `apply_patch`, изменение существующего файла вне проекта | Отдельный запрос fileChange; исходные байты сохранены | Разрешение меняет искусственный текст. |
| `exec_command`, `cat` вне проекта | Запрос commandExecution; отказ не передаёт содержимое локальному провайдеру | Этот конкретный отказ не доказывает, что политика спрашивает перед каждым чтением. |

Таким образом, проверка не ограничена отказом одной shell-команды. Прямой
инструмент изменения файла проверен отдельно, включая существующий файл.
Доказательства: `codex-denial-*`, `codex-direct-edit-*`, `codex-existing-*`,
`codex-read-denial-*`; события содержат только фиктивные пути и данные.

Вторая серия — 12 реальных native `command/exec` операций: чтение/запись
внутри/вне проекта для full, read-only, workspace-write. Все четыре full прошли.
Остальные восемь завершились **ошибкой запуска bubblewrap**, с сообщением об
unsupported host mount у app-server socket directory. Это не успешная проверка
запрета записи. Изоляция read-only/workspace-write в данной среде не подтверждена.
Ни тест, ни приложение не переключали отказавший sandbox на полный доступ.
Доказательства: `codex-native-results.json`, `codex-native-summary.log`.

Локальное изменение использует отдельную фабрику `WorkspaceStore.newProfile()`.
Новые профили имеют `codexUntrustedApproval=true`, `codexConfirmActions=true`.
Декодирование отсутствующего поля сохраняет старое поведение. Copy и JSON
сохраняют новый флаг. Оба адаптера принимают `untrusted`; проверка native readback
сохраняется. Ошибка политики не разрешает действие автоматически.

Новая подпись RU/EN: **«Подтверждать недоверенные команды» / “Confirm untrusted
commands”**. Пояснение прямо исключает обещание границы папки проекта. Старые
профили с `on-request` сохраняют соответствующую подпись, чтобы не выдавать эту
политику за `untrusted`. Отключение подтверждений пользователем по-прежнему явно
меняет эффективную политику на `never`.

Robolectric проверяет создание через настоящий редактор, сохранение, повторное
открытие, второе сохранение и чтение из хранилища, включая строку запуска.
Отдельный тест проверяет copy и старые профили `never` / `on-request`.
Это не проверка жестов и интерфейса на телефоне.

## Claude Code

`WorkspaceStore.Session.claudeMode="manual"` → `ClaudeCode` →
`claude-chat.cjs` (`--permission-mode manual`, can_use_tool, ответ deny).
Сохранённый режим не подменяется bypass-режимом. Профильные тесты проверяют
сохранение, повторное открытие и второе сохранение.

Настоящий **Claude Code 2.1.296**, собственный HOME/CLAUDE_CONFIG_DIR и локальный
синтетический Anthropic-провайдер:

- Native **Write внутри проекта**: запрос; отмена не создаёт файл; разовое
  разрешение создаёт точный искусственный текст.
- Native **Write вне проекта**: тот же результат отказа и разрешения.
- Native **Read внутри проекта**: без запроса; фиктивный текст передан локальному
  провайдеру как tool_result.
- Native **Read вне проекта**: запрос; отказ не передаёт текст; разрешение передаёт.
- Тест штатного контроллера проверяет завершение собственного дочернего процесса
  и сохранение отдельно созданного фиктивного постороннего процесса.

Доказательства: `claude-native.log`, `claude-outside.log`, `claude-read-results.json`,
`claude-read-inside-results.json` и сценарии рядом. Это реальные операции CLI,
но ответы модели искусственные. Отдельная серия shell-команд Claude и проверка
Android/proot на телефоне здесь не выполнены. `manual` оставлен без изменения:
это работающее подтверждение инструментов, а не ОС-изоляция проекта.

## Где находится авторизация

Код запусков использует фактическую среду сессии и HOME CLI; рабочие файлы не
читались. Codex обычно использует `$CODEX_HOME` / `$HOME/.codex`; Claude-контроллер
читает историю из `CLAUDE_CONFIG_DIR` / `$HOME/.claude`. Наличие токена в конкретной
установке или точное содержимое native хранилищ здесь не устанавливалось.

Gemini API: `GeminiApiKeyVault.encrypt/prepare/write` сохраняет в профиле ciphertext,
связанный с profile ID через AAD. Ключ AES создаётся Android Keystore. Перед запуском
нужен открытый текст в приватном handoff `keys/<profile UUID>.key`. Consumer
`gemini-control.js.takeApiKey` читает его и передаёт ключ окружением своему CLI.
OAuth/Vertex используют native Gemini/Google авторизацию; содержимое ADC не читалось.
`authEnvironment` отделяет выбор API/Vertex и создаёт приватные временные настройки.

OpenCode `ai-agents-control.js.start(root)` задаёт отдельные XDG config/data/cache/state
для connection root, удаляет унаследованные переменные API-ключей из известного
списка и создаёт пароль loopback-сервера. Это не доказательство шифрования native
авторизационных файлов и не изоляция от другого процесса того же пользователя.

## Gemini: жизненный цикл искусственного ключа

`GeminiApiKeyVaultTest` проверяет AES-GCM, случайный ciphertext, AAD profile binding,
очистку переданных массивов, отсутствие plaintext в JSON профиля/команде и права
файла. Использован искусственный AES-ключ, не настоящий Android Keystore.

`gemini-lifecycle.cjs` вызывает настоящий consumer и запускает только собственный
bash-процесс с тем же EXIT-trap механизмом, который генерирует `SessionShell`.

| Сценарий | Остаток |
| --- | --- |
| Корректный ключ, чтение | Файл удалён; исходно 0600, каталог 0700. |
| Неверное содержимое после чтения | `finally` удаляет файл. |
| Неверные права 0644, отказ до чтения | Consumer оставляет файл; это искусственно изменённые права, не права штатного producer. |
| Обычный выход оболочки до чтения | EXIT trap удаляет файл. |
| SIGKILL собственной оболочки до чтения | Trap не выполняется; файл остаётся. |

Источник A-AUTH-01: cleanup после `read` не охватывает crash до него.
`WorkspaceController.rollbackUnstarted` вызывает `discard` при ошибке создания
терминала; `prepare` убирает старый target при следующем запуске. Это не гарантирует
немедленную очистку после аварии. Права 0600 защищают от других Unix-пользователей,
но не от агента с теми же правами и доступным bind-путём. Достижимость конкретного
остатка из другого агента на телефоне не проверена.

Предлагаемое исправление отдельно: одноразовый приватный канал вместо постоянного
handoff-файла либо проверяемый lifecycle с cleanup после завершения принадлежащего
запуску процесса. Не удалять файлы работающего запуска. Не обещать стирания
неизменяемых JS strings или аппаратной защиты Keystore без отдельной проверки.
Сценарий кнопки «Отмена» и авария полного Android дерева процессов пока не проверены.

## Резервная копия и восстановление

Производственный `workspace-backup.py.create/inspect/restore` обработал только
фиктивный профиль и HOME. В tar.gz реально вошли и восстановились шесть категорий
маркеров: Codex auth, Claude credentials, Gemini OAuth, OpenCode auth, SSH private key,
проектный `.env`. Метаданные профиля прошли roundtrip. Искусственный vault ciphertext
копируется как ciphertext, не расшифровывается. Архивы созданы с mode 0600.
Это gzip/tar, **не зашифрованный архив**.

`WorkspaceBackupUi.selectiveInventory` и подтверждения предупреждают, что архив
содержит/может содержать секреты. `settingsScope` предупреждает о непереносимости
Android Keystore. `WorkspaceBackupImport.prepare` очищает сохранённые SSH/Gemini
vault-поля при импорте профиля и меняет идентификаторы. Это не удаляет native
авторизации CLI из восстанавливаемого HOME.

- Локальное хранение: созданные backup-файлы содержат маркеры в открытом виде.
- Явный экспорт: пользователь выбирает состав и подтверждает; место назначения
  может оказаться общим хранилищем или внешним документ-провайдером.
- Автоматическая передача: не обнаружена в исследованной цепочке create/inspect/restore.
  Это не утверждение об отсутствии любой передачи данных приложением.
- Предлагается явно добавить в RU/EN предупреждение «архив не зашифрован» и
  отдельную возможность исключить авторизации. Эти изменения пока не реализованы.

Доказательства: `backup-results.json`, `backup-profile.log`, `backup-probe.py` и
44 штатных Python-теста (`backup-regression.log`). Фикстура повторно использовала
свой тестовый HOME с предыдущим восстановлением: в повторный архив вошла и эта
фиктивная копия. Это не тест чистого устройства и не аудит всех возможных членов
полного Linux/rootfs-архива. Все шесть исходных маркеров остались неизменны.
Проверка восстановления вне HOME правильно отказала; сценарий затем использовал
допустимый новый подкаталог фиктивного HOME.

## Проверки, ошибки стенда и ограничения

Проверено заново: целевые JVM/Robolectric, Node адаптеры Codex/Claude/Gemini/OpenCode,
native случаи выше, Python backup и локализации. Полный modern Lint пяти модулей:
0 ошибок, 236 предупреждений. Это анализ кода, не проверка release APK.
Итог: **76 JVM-тестов, 0 ошибок/отказов/пропусков** (`jvm-summary.json`).
Код исправления: `752b1b1dac17f77e0d7f67581b0c433c76c045f3` на ветке `work/rollback-live-actions`.
Проверки X11/драйверов/установки ОС не запускались: эти механизмы не менялись.
APK не собирался и не устанавливался. Старые тестовые APK не содержат новый policy.

Сохранены первоначальные ошибки стенда: устаревший UI-test locator после изменения
accessibility label; неверное ожидание, что конкретный Codex cat не спросит
разрешения; поиск tool_result только в последнем сообщении fake provider. После
исправления проверок соответствующие сценарии повторены. Эти ошибки не объявлены
найденными дефектами приложения. Ошибка native sandbox осталась непроверенным
ограничением среды, а не превращена в PASS.

## Что проверить далее

1. Gemini и OpenCode: локальная модель должна вызвать настоящие файловые и shell
   инструменты. Отказ и разрешение проверить по байтам внутри/вне проекта.
2. Телефон: новый Codex-профиль → save/reopen → команда и direct edit → отказ;
   проверить отсутствие записи. Отдельно повторить старый профиль без миграции.
3. Телефон: read-only/workspace-write должны либо реально ограничивать запись,
   либо явно отказывать в запуске. Запретить обход через переход на full/never.
4. Телефон: Gemini artificial API key, ошибка старта, отмена, завершение приложения
   до/после handoff; проверить остатки без использования реального аккаунта.
5. Телефон: fake HOME backup через SAF, импорт в отдельное место, предупреждения,
   права, свободное место, прерывание и отказ без перезаписи рабочей среды.

Ни одна из этих проверок на телефоне не выполнена помощником в этом этапе.
Пользовательская приёмка компоновки test1 относится к другой задаче.
Изменение новых Codex-профилей сохраняется отдельным локальным коммитом от отчёта.
Push, публикации, изменения тегов/Components и настроек существующих агентов нет.
