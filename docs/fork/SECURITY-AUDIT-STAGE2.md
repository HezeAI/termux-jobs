### Исключённые области и отдельные направления

- **A-DRIVER-01 / P2:** содержимое/исполнение драйверов и полный binary audit.
  SHA/ELF подтверждают целостность/формат, не безвредность. Следующий отдельный
  этап — помощник по коду/бинарникам и разработчик на тестовом устройстве; сейчас
  не запускать неизвестные `.so`. Источник: карта первого этапа.
- Полный сетевой трафик сторонних CLI, SDK, транзитивных библиотек и облачного
  провайдера. Текущая карта основных путей не является исчерпывающим перехватом.
- MCP и плагины: исключены из текущего объёма аудита и работ, **не проверены**; импорт настроек не делает их доверенными.
- Хранение/резервирование закрытого ключа подписи, аппаратные гарантии Keystore,
  независимый внешний аудит, враждебные процессы того же UID и разработка новой
  OS-песочницы. Никаких гарантий по отсутствию секретов или компрометации не дано.
- Чистая установка всех окружений, медленная реальная мобильная сеть и driver/GPU
  регрессии — отдельная приёмка, не следуют из проверки существующей Ubuntu.
- Накопление вложений/обрывы — **отдельная незакрытая задача**, без исправления
  в test6. [План и baseline](MEDIA-CONTEXT-INVESTIGATION.md): PNG/JPEG/WebP,
  кадры видео, большие тексты/документы, tool/MCP results, бинарные карточки и
  последующее чтение; Codex сначала, затем отдельные Claude/Gemini/OpenCode.
  Помощник готовит измеряемый кандидат; разработчик проверяет прежний внешний
  маршрут/повторное открытие. Локальный provider не заменяет эту приёмку.
- Рабочие чаты, авторизация, старые журналы, опубликованные APK/теги/Components:
  не обследуем и не изменяем без отдельной необходимости/авторизации.

### Частичная пользовательская проверка резервной копии — 2026-11-04

По уже присланным скриншотам и уточнению разработчика засчитан только частичный
просмотр **выборочной формы резервного копирования на русском языке** на телефоне.
Это сведения пользователя, не самостоятельно выполненная проверка помощника.
Скриншоты не подтверждают экспорт, содержимое архива, восстановление, отсутствие
секретов, совместимость старых архивов или пассивность квитанций. Не установлены
поведение checkbox при новом открытии и все ветви предупреждений. Полная форма,
EN, SAF, ошибки/отмена экспорта и чистое восстановление остаются открытыми.
Повторять уже показанное оформление RU без изменения интерфейса не требуется;
следующая проверка должна покрыть перечисленные непоказанные действия.

## Gemini: исправление аварийного остатка

Затронуты `GeminiApiKeyVault.prepare`, `GeminiKeyBroker`, `GeminiCli.command`,
`SessionShell`, `WorkspaceController.create` и `gemini-control.js.takeApiKeySocket`.

Новые запуски не создают `keys/<profile>.key`. Хранилище ciphertext, alias Keystore,
AAD profile binding и сохранённые профили не мигрируют. Новый broker получает
снимок ID/ciphertext и расшифровывает его только после проверки потребителя.
До этого, в том числе во время длительной подготовки пакетов, plaintext не нужен.

Передача одноразовая. Проверяются run UUID, kernel UID клиента, принадлежность
его PID дереву конкретного терминала и время старта владельца из `/proc/<pid>/stat`.
Неизвестная принадлежность, умерший владелец и повторное использование PID приводят
к отказу. Завершение старого broker не закрывает broker другого запуска.

- До привязки созданного терминала предусмотрено ожидание до 30 секунд.
- Нулевой PID ещё не запущенного терминала не считается живым подтверждённым
  владельцем и не разрешает выдачу ключа.
- Пока потребитель не пришёл, watcher проверяет владельца раз в секунду.
- Запрос канала и потребитель имеют ограничение ожидания 10 секунд.
- Ошибка создания терминала закрывает именно локальный объект этой попытки.

## Сетевой запрет последующих проверок

У `unshare` в этой среде exit code 0 не создал изоляцию: namespace остался тем же,
и дочерний процесс достиг собственного sentinel-сервера родителя. Эту проверку
не считают PASS. Возможности ядра проверены отдельными безопасными пробами.

Тестовый `local-network-only.c` использует seccomp user notification и ADDFD.
Он применяется к Node-фикстуре и всему дереву запускаемых CLI, включая exec/fork.
Системный firewall, маршруты, DNS и подключения приложения не меняются.

- Socket descriptors создаёт supervisor и передаёт фильтрованному процессу.
  Перед exec закрываются унаследованные дополнительные descriptors.
- connect/bind выполняются supervisor на сохранённом descriptor, по скопированному
  и проверенному адресу. Для этих вызовов нет CONTINUE и гонки повторного чтения
  sockaddr из памяти CLI.
- Разрешены только 127.0.0.1/::1 и endpoints, которые зарегистрировал bind этого
  же дерева. Чужой localhost-сервис не является разрешённым провайдером.
- Разрешённый Unix transport ограничен собственными зарегистрированными abstract
  endpoints; UDP, raw/packet, нестандартные stream-протоколы, TCP Fast Open,
  новые io_uring и BPF запрещены.
- Неподдерживаемый kernel API или невозможная проверка дают отказ, без обхода
  через прокси, preload или снятие фильтра.
- Контрольные пробы проверяют собственный listener, чужой localhost, TEST-NET IPv4,
  IPv6, UDP, packet, нестандартный stream, Fast Open, прямой native syscall
  и наследование после exec. Локальный
  sentinel вне фильтруемого дерева не получил соединения.

Новый guard также наблюдал и заблокировал обращения OpenCode к чужим localhost
портам **1234, 11434, 8000**. Это фактические попытки в новом запуске, не восстановленный
след ранней пробы. Они показывают, что правильный model baseURL не исключает иных
обращений CLI. Контент таких сервисов не запрашивался после kernel-отказа.

Guard находится только в тестовых скриптах и не входит в APK. Его kernel API
не добавляет требований к установке приложения.

Это ограничитель сети контролируемых тестовых процессов, а не полная изоляция
файловой системы или независимый аудит защиты от намеренно враждебного процесса
того же UID. Полный трафик CLI в обычной среде остаётся отдельной задачей.

### Состав, предупреждение и формат

Только при выборе библиотеки **и отдельного выключенного по умолчанию пункта**
«Данные подключений OpenCode» `workspace-backup.py.opencode_sources/create_opencode_tar`
добавляют отдельный компонент `opencode-connections.tar.gz`. Собираются только
connection IDs из её профилей, с частями `config`, `data`, `state`, `session-links`
и `receipts`. Один общий connection ID не дублируется для нескольких пресетов.

Возможны API-ключи/токены и авторизация провайдеров, настройки/плагины/команды,
сообщения, результаты инструментов, native-логи, внутренние снимки файлов проектов
и текст прежних решений. На фикстуре native 2.0.28 действительно создал SQLite DB,
`data/opencode/log` и `data/opencode/snapshot`. Копия не зашифрована. Исключение
самой проектной папки не исключает её прежнее содержимое внутри истории/снимков.
В обеих формах RU/EN это явно указано до согласия на создание. Без отдельного
выбора данные не включаются; предупреждение объясняет неполное восстановление.
Отключение библиотеки снимает выбор подключений. Обновление формы сохраняет
явный выбор. Manifest фиксирует выбор и фактическое включение отдельно.
Недоступная оценка размера подключений не блокирует экспорт остальных данных.

Верхний `cache`, runtime-файлы вне перечисленных частей и работающие процессы
не переносятся. Проектные папки, внешняя авторизация и вложения вне этих каталогов
требуют отдельного выбора; их копии внутри native данных всё равно включаются.
Ссылки/специальные файлы внутри компонента отклоняются без чтения внешней цели.
SQLite копируется online backup с учётом WAL и quick_check; sidecars не подменяют
согласованный снимок. Межфайловая атомарность и согласованность всех баз не обещаются.

Наличие нового компонента задаёт **manifest version 3**. Новый reader поддерживает
старые версии **1 и 2**. Старый reader отказывает для v3, вместо тихого пропуска
подключения. Без нового компонента сохраняются прежние версии создания.
Состав и ограничения: [резервные копии](BACKUP-RESTORE.md).

### Восстановление и права

`inspect_opencode_tar` проверяет индекс, UUID, состав и отсутствие ссылок.
`restore` сначала извлекает компонент отдельно и возвращает проверенные источники.
`WorkspaceBackupImport.prepare/apply` и `OpenCodeBackupRestore` готовят приватную
копию, атомарно публикуют новый каталог и связывают новые пресеты с новым UUID.
Сохранённые policy-поля не заменяются разрешениями из квитанций. Существующие
подключения/авторизации не заменяются. Общие подключения нескольких пресетов
остаются общими внутри новой копии; повтор импорта создаёт независимую копию.

До apply/при ошибке подготовки удаляются только собственные новые staging-копии.
Коллизия не заменяет существующий каталог; повтор использует новый UUID.
Пресет сохраняет `restoreReview`, не получает live handle, не запускается при
импорте. Перед явным запуском требуется проверка среды/папки, адресов провайдеров,
плагинов и команд. В старом архиве без компонента импорт по-прежнему возможен,
но OpenCode нужно настроить отдельно; чужую действующую авторизацию он не подбирает.

### Полный native-цикл и квитанции

Тест использует настоящий закреплённый **OpenCode 2.0.28**, Node **22.22.1**,
production bootstrap/controller, настоящий Python create/inspect/restore,
Java importer, atomic WorkspaceStore save/reopen и generated launch восстановленного
профиля. Подменены guest mount/socket пути Android/proot и GUI-среда (Robolectric).
Это не установка/приёмка APK на телефоне и не настоящий вход в аккаунт провайдера.

CLI/JDK/SDK переиспользованы; данные чистые: новые HOME/XDG/config/data и библиотека,
искусственный ключ только в настройках локального провайдера. Исходные connection
и runtime HOME переименованы и сохранены перед повторным запуском. Старую

берёт только прежний проверенный native бинарник; ничего не устанавливает.
Сеть ограничена kernel guard: только listeners собственного тестового дерева.

Для shell и direct Write проверяются отдельные полные циклы:

1. Native инструмент спрашивает разрешение; фикстура явно отвечает Allow once.
2. Создаётся реальный эффект на искусственном файле и сохраняется квитанция.
3. Экспорт выполняется с настоящими native данными; профиль импортируется в чистое
   app storage, получает новый ID/connection UUID, сохраняется и перечитывается.
4. После явного запуска прежние native session ID, история и квитанции видимы.
   До нового запроса нет inference/нового разрешения. Байты и mtime тестового
   файла не изменяются: квитанция сама не воспроизводит действие.
5. Идентичная shell-команда либо новый Write того же файла снова требуют разрешения.
   Тест отвечает No; исходный результат и mtime сохраняются. Разовое Allow из
   исходного запуска не переносится. Readback действующей policy возвращает `ask`.
6. После отказа native OpenCode прерывает текущий шаг. Отдельный следующий запрос
   успешно получает ответ; провайдер видит прежнюю историю. Это не подмена отказа
   автоматическим продолжением отменённого инструмента.

Первичные неудачные пробы сохранены. Стенд сначала ошибочно выдавал tool call
служебному запросу без tools; затем ожидал ответ в отменённом шаге. Для Write
предварительная проверка карточки ожидала абсолютный путь, хотя native edit
представляет относительный. Эти допущения исправлены в фикстуре; запрет не
автоматически одобряется и отсутствие карточки не считается отказом.

`npm install -g @google/gemini-cli@latest`. Это не управляемое обновление нашего
закреплённого runtime. Установка при неудаче испускает `update-failed`;
`setUpdateHandler` добавляет `type:error` в native UI history.

Проверка запускается асинхронно после создания React UI и не ожидается перед
чтением ввода. Её ошибку нельзя саму по себе объявлять причиной отказа запуска.
Native relaunch отдельно может ждать незавершённое обновление до 30 секунд.
Воспроизведён exact updater error callback с искусственным spawn, без запуска npm.

Локальная policy использует **поддерживаемые настройки**:
`general.enableAutoUpdate=false`, `general.enableAutoUpdateNotification=true`.
Последняя инструкция пользователя сохраняет проверку версий; ранний вариант
«отключить обе» заменён. Системный per-run слой native merge выше user/workspace:
проверено настоящим `loadSettings`, включая противоречащие искусственные файлы.
Файлы пользователя не переписываются. В auto отсутствует `security.auth`, прежний
способ входа сохраняется. Внешняя system policy не подменяется; конфликт даёт
явный безопасный отказ. Установленные CLI не обновлялись.

Существующий hash-pinned loader отмечает сообщения **только callback обновления**
`jobsNotice:cli-update` и задаёт `type:info` до native addItem. Native recorder
сохраняет только type/content и теряет дополнительный признак; настоящий
useHistory/recordMessage/reopen проверен отдельно. Поэтому будущие уведомления
после открытия истории тоже не становятся error. `GeminiChat` проецирует их как RU/EN уведомления и не
считает ошибками сессии/ответа. Текст произвольной ошибки не служит признаком
обновления. Auth error и обычные ошибки остаются ошибками, даже если затем пришло
уведомление. Сохранённая native история вручную не редактируется.

### Обычный путь и ссылки

Установщик делает tar extraction + mv; сам он ссылку runtime не создаёт.
Но `$HOME`, его предок или runtime могут быть ссылкой: штатный bootstrap передаёт
логический путь, Node загружает канонический URL. Прежний loader сравнивал эти
каталоги буквально и пропускал инструментацию при несовпадении.
Наличие ссылки на телефоне пользователя не установлено; это подтверждённый
условный дефект контроллера, не объявленная причина его конкретного телефона.

Контроллер теперь передаёт **один fs.realpathSync runtime** и в argv, и в
`JOBS_GEMINI_BINARY` дочернего процесса. Файлы CLI не меняются. Стенд больше
не исправляет alias через realpath сам. Проверяются обычный файл и runtime alias,
новый и повторный запуск. При отсутствии UI binding/неподдерживаемой разметке
controller chat-send явно возвращает `NOT_READY`, accepted отсутствует;
модельный запрос не выполняется. Работающий процесс не признаётся готовым чатом.

Свежие проверки: 22 JVM-метода без отказов/ошибок/пропусков, включая один
явный native-метод с 16 API/Vertex shell/write No/Allow сценариями; 10 Node suites,
из них отдельные native settings/update и handler-guard проверки. Повтор после
канонизации обоснован изменением startup path, остальные агенты не перезапускались.

### Ключ: границы доказательства

Настоящий bootstrap, controller, Gemini CLI 0.64.0 и Unix/IPC chat выполнены с
искусственным HOME/проектом/ключом. Native Node и runtime переиспользованы;
способ запуска контроллера соответствует приложению, но Android/proot mount,
Java broker credentials и Keystore не воспроизводятся PTY-стендом.
Kernel network guard разрешает только listeners тестового дерева. Native context
filename искусственный, Git discovery ограничен тестовым корнем.

В четырёх случаях (обычный путь/ссылка × первый/повторный запуск) broker получил
точный run handshake, controller получил ключ, native chat принял сообщение,
локальный provider получил этот искусственный ключ и вернул **HTTP 401**.
Отказ виден в error-строке; CLI остался жив, owned controller завершён штатно.
Скаляр `authError` остаётся false: выбор API-key режима и надпись native
«Authenticated with gemini-api-key» **не означают проверку ключа сервером**.
Отказ проявился на реальном запросе. Исчезновение update-плашки не является
доказательством исправления запуска. Ни реальный Google-вход, ни handoff телефона
этими результатами не закрываются.
