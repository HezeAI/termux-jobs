# Подготовка релиза

## Общие правила

Этот порядок применяется к каждому новому выпуску Termux Job’s на GitHub.
Авторизация определяется текущей задачей пользователя. Правила сами по себе
не разрешают будущие commit/push/tag, установку APK или публикацию.
Уже данное разрешение учитывай в его пределах и не запрашивай повторно без причины.

**Голосовой ввод остаётся удалённым.** Не возвращай микрофон, распознавание,
связанные обработчики, диагностику или разрешение в сборки без отдельного
поручения разработчика. Прежнее ожидание проверки на телефоне не отменяет запрет.
История решения перенесена в [исторический отчёт test40](VALIDATION-test40-composer-instructions.md#историческое-уточнение-порядка-выпуска--2026-11-04).

GitHub release titles/descriptions and new public release notes must be written
in English unless the developer explicitly requests another language. Keep the
in-app update highlights and compatibility notes localized in both Russian and
English. This is the developer's standing preference for future updates.

End every GitHub release description with this exact credit line, as requested
by HezeAI: `AI development assistance: OpenAI Codex`. Keep HezeAI credited as the fork developer;
this line identifies AI assistance.

Сохраняй прежние APK, теги и бинарные Components. Для уже опубликованной версии
ради оформления меняй только описание и относящуюся документацию: не заменяй APK,
update.json или бинарные ресурсы, не передвигай тег. Последующее исправление
документации в основной ветке не требует пересборки неизменённого APK.
Условия отдельной публикации исходников Components приведены в разделе лицензий.
Старые резервные файлы, включая APK 1499, сохраняй; не пересобирай и не заменяй
их в рамках нового выпуска. Разовые указания для APK 1493–1500 перенесены в
[исторический отчёт](VALIDATION-2.1.5-test5.md#исторические-указания-для-apk-1493-1500).
Исторические разрешения и запреты относятся только к указанным там задачам;
они не определяют авторизацию нового выпуска.

## Состав изменений и документация

Определяй итоговый набор изменений относительно **последнего опубликованного
стабильного релиза**, а не промежуточной тестовой сборки. Учитывай изменённые
и новые файлы. Исходники, документация, патчи и материалы сборки должны описывать
финальную версию и соответствовать APK. В описание включай только завершённое
поведение, фактически вошедшее в APK. Незавершённые функции, известные существенные
дефекты и ограничения указывай явно. Не обещай ускорение, совместимость или
исправление сбоя без доказательств; улучшение отображения или один успешный
повтор не доказывают исправление причины.

### Версия и совместимость

1. Обнови versionName/versionCode под итоговый состав. Публичный versionCode
   должен превышать все уже выданные основные и резервные APK.
2. Для совместимого обновления сохраняй package ID и сертификат. Укажи изменения
   требований Android, форматов, миграций, необходимость перезапуска процессов,
   сбросы, потерянные или непереносимые данные и причины до установки — в RU/EN
   описаниях обновления и release notes. Требования старого обновлятора — ниже.
3. Не обещай сохранность данных или возможность отката без проверки. Резервный
   APK не является резервной копией пользовательских данных. Не очищай данные
   и не переустанавливай окружения автоматически ради обновления.

### Переход от принятого тестового APK к стабильному

Зафиксируй версию, SHA-256 и исходники APK, принятого разработчиком на телефоне,
а также сообщённый им объём проверки. Сохраняй этот функциональный код.
Меняй необходимые релизные метаданные по правилам версии выше; versionCode
не понижай. Стабильный versionName не содержит суффикс test, а GitHub Release
публикуется с prerelease=false.

Если нужны дополнительные изменения поведения, явно перечисли их отдельно
от принятой основы и проверь затронутые пути. Не представляй изменённое поведение
как уже принятое на телефоне. В отчёте покажи diff и проверку идентичности
неизменённых входов; условия переиспользования определены в разделе проверок.
Пересборка даже только с новыми метаданными требует всех обязательных проверок
[финального APK](#финальный-подписанный-apk) и релизных проверок проекта.

Rollback-APK создавай и публикуй только по отдельному поручению пользователя.
Обычный стабильный выпуск не включает его автоматически. Такое поручение
не отменяет проверки совместимости данных и защиты прежних файлов.

## Лицензии, авторство и соответствующие исходники

Этот раздел обязателен перед релизом приложения, добавлением/обновлением
распространяемых компонентов и публикацией исходников к ним. Для новых и
обновлённых сторонних библиотек, инструментов, образов, моделей, шрифтов,
значков и других ресурсов проверь источник, точную версию, авторство, лицензию
и применимые условия распространения. Не приписывай upstream-разработку форку
и не создавай впечатление одобрения проекта владельцами названий/логотипов.
Сохраняй исходные лицензии, copyright и предусмотренные ими исключения.

Конкретные уведомления, версии, ссылки, источники и результаты проверки храни
в [THIRD_PARTY_NOTICES](../../THIRD_PARTY_NOTICES.md), относящихся манифестах
компонентов и отчёте проверки. Для Components используй также их
[каталог и уведомления](https://github.com/HezeAI/termux-jobs-components).
Этот порядок не заменяет конкретные условия лицензий.

1. Проверь обязательные copyright, NOTICE, LICENSE и условия атрибуции.
   Включи требуемые тексты в финальный APK и распространяемые архивы; проверь
   их наличие в готовых файлах. Согласуй README, Releases и «О программе».
2. Где требуется соответствующий исходный код, сверь его с точной бинарной
   версией и нашими изменениями. Включи необходимые патчи и материалы сборки.
   Ссылка только на главную страницу upstream или репозитория дистрибутива
   не подтверждает соответствие исходников. Проверь конкретные файлы и доступ.
3. Публикуй исходники отдельными ресурсами с версиями, размерами, SHA-256 и
   прямыми ссылками рядом с соответствующими бинарными ресурсами. Не включай
   архив соответствующих исходников в автоматическую загрузку приложения или APK.
   Это не запрет поставлять рабочий код приложения в исходной форме, например
   исполняемые Python-модули. Для файлов,
   перечисленных в метаданных исходников, проверь доступность, полный состав
   и контрольные суммы. Укажи, проверялась ли подпись самих метаданных.
4. Сохраняй URL, имена, содержимое, размеры и SHA-256 уже опубликованных
   компонентов. Не пересоздавай релиз и не заменяй существующие ресурсы ради
   документации. Лицензии, уведомления и исходники добавляй отдельными файлами.
   Если нужны изменения бинарного компонента, сначала объясни причину и влияние
   на установленные версии; не расширяй разрешение на документацию до такой замены.
5. Проверь публичное скачивание добавленных файлов и их контрольные суммы.
   Сверь прежние идентичности бинарных ресурсов и каталоги приложения. Проверь
   штатный загрузчик с ожидаемыми хешами. Различай реальную повторную загрузку,
   переиспользованное доказательство и проверку только метаданных/ссылки.
6. Зафиксируй охват: какие компоненты, версии и условия проверены, какие
   исходники/уведомления доступны и какие вопросы остались. Не выдавай частичную
   проверку за полное соблюдение лицензий. При препятствии для распространения
   укажи конкретный файл, требование и способ исправления до его дальнейшей
   публикации. Проверка относится и к ранее опубликованным Components.

### Ревизии Components и проверка загрузчика

Публикуй новую ревизию, если изменились распространяемые файлы компонента.
Сравни состав, размеры и SHA-256 с опубликованной ревизией, а не только версию
upstream. Например, исправление обработчика RTK внутри APK не требует новой
ревизии RTK, если файлы распространяемого компонента не изменились.
Старые ресурсы не перезаписывай; правила лицензий и соответствующих исходников
выше применяются и к новой ревизии.

Для обновлённого компонента проверь публичную загрузку, ожидаемые размер и SHA-256,
первую установку, обновление прежней версии и повторное использование совместимой
установки без лишней загрузки. Проверь сохранение относящихся настроек и данных;
при ошибке обновления рабочая установленная версия должна сохраняться.

При изменении загрузчика проверь обычный маршрут и резервный API-маршрут
по отдельности. Для обоих проверь отмену, обрыв и повторную попытку, отказ при
неверном размере и SHA-256. Не выдавай успешный резервный маршрут за подтверждение
обычного. Не превращай проверку метаданных или локальную фикстуру в доказательство
фактического публичного скачивания. Применяй эти проверки к затронутым загрузчикам
приложения, компонентов и установочных архивов окружений.

For the separate `HezeAI/termux-jobs-components` repository, keep component details,
compatibility, source credits and licenses in its English README and exact
versions/sizes/hashes in `components.json`. Update that overview when components
are added or revised. Component release descriptions may stay brief: the set
identifier, a README link and the credit line above. Keep published tags and
binary assets immutable. This does not shorten application release notes or
replace the application's localized updater/compatibility requirements.

## Выбор объёма проверок

До изменения определите функции, вызывающие и общие механизмы, зависимости и
значимые риски. План и правила переиспользования результатов описаны в
[TESTING.md](TESTING.md). Профильные проверки достаточны при обоснованно узком
влиянии; полный применимый набор нужен при широких изменениях, изменении общих
механизмов или неопределённых зависимостях. Проверки безопасности процессов,
изоляции, отмены и восстановления сохраняются для затронутых путей.

Не запускайте X11, установку окружений и испытания драйверов/компонентов только
из-за изменений редактора инструкций или оформления чата; сначала проследите
косвенные зависимости. Проверка хешей упаковываемых X11-файлов не равна запуску
стола и остаётся частью применимой сборочной проверки.

В отчёте отдельно укажите «проверено заново», «переиспользовано» и «не проверено».
Для переиспользования подтвердите совпадение значимых исходников, конфигурации,
зависимостей и условий; один старый успешный лог недостаточен. Для промежуточных
APK явно обоснуйте объём компиляции, синтаксических/ресурсных и статических проверок
по [Lint](LINT.md). Полный современный Lint всех пяти модулей перед публичным
релизом остаётся обязательным. Изменение только документации не требует сборки
APK. Не создавайте полные копии SDK/rootfs ради прогона, сохраняйте компактные
доказательства и не удаляйте существующие данные без разрешения.

### Modern Lint

Перед публичным релизом выполни `bash scripts/verify-modern-lint.sh`:
анализ всех пяти модулей, отсутствие ошибок загрузки правил и блокирующих находок.
Старый lint из APK-цепочки сам по себе не подтверждает этот gate. Неразобранные
предупреждения и ограничения версии SDK указывай в отчёте; не скрывай их общей
baseline/disable-настройкой.

### Debug в CI и проверка release

`testDebugUnitTest` использует вариант debug. Сохраняй внутренние debug-этапы,
необходимые существующим тестам. Отдельный `assembleDebug` в текущем CI проверяет
сборку debug APK; он не является условием запуска этих JVM-тестов.
Такой APK может храниться как внутренний артефакт GitHub Actions, но не входит
в состав стабильного GitHub Release и не поступает в стабильный канал обновления.
Выпускать или предоставлять debug APK при каждом релизе не требуется.

Основная проверка выпуска — сборка варианта **release** из финальных исходников
и проверка именно окончательного **подписанного release APK**. Успех debug-тестов
или `assembleDebug` не заменяет сборку release и [проверки финального файла](#финальный-подписанный-apk). Неподписанный промежуточный APK также не
заменяет проверку подписанного файла, который будет опубликован.

Сборка, подпись и аудит release выполняются существующим разрешённым порядком
локально либо в подходящем CI. В отчёте разделяй варианты debug/release,
локальные проверки и GitHub CI; указывай коммит исходников, коммит workflow,
задачи и фактически проверенный APK. Если CI проверил только debug, а release
собран и проверен локально, напиши это прямо. Не называй такой CI проверкой
опубликованного release APK.

## Результат аудита и приёмка

Перед выпуском кратко зафиксируй в отчёте и значимых ограничениях выпуска:

- Что исправлено и действительно вошло в финальный APK.
- Что принято разработчиком на телефоне.
- Что не проверено, с причиной и оставшейся проверкой.
- Что исключено по согласованию с разработчиком и в каких границах.

Для каждого результата указывай версию APK или коммит, источник проверки
(самостоятельный стенд/автотест, сообщение разработчика с телефона либо иной
явно названный источник) и относящиеся доказательства. Переиспользованные
результаты отмечай по правилам раздела проверок. Пропущенная проверка не считается
успешной, а стенд не заменяет приёмку телефона. Согласованное ограничение охвата
не превращает непроверенную область в PASS.

Разделяй подтверждённый дефект и непроверенный сценарий. «Не проверено» не означает
«проблема не устранена». Для утверждения о дефекте укажи конкретное поведение,
версию, условия и источник. Не добавляй общие заявления об отсутствии безопасности
или сертификации без конкретного основания. Не заявлявшаяся сертификация сама
по себе не является ограничением продукта. Значимые ограничения сохраняй
в release notes; подробный охват и доказательства — в отчёте именно этой версии.

Полный повтор аудита при каждом релизе не требуется. Повторяй затронутые проверки
по изменениям и рискам, сохраняя условия подтверждённого переиспользования.
Известная критическая регрессия, утечка секретов или неподтверждённая безопасность
остановки затронутых процессов **блокируют выпуск** независимо от числа успешных
тестов. Приёмка проводится в согласованном объёме, а её ограничения сохраняются
в итоговом отчёте и описании выпуска там, где они значимы для пользователя.

## Финальный подписанный APK

Собери release из финальных исходников в изолированной среде выбранным
разрешённым порядком. Для **каждого выдаваемого APK**, включая промежуточный,
проверь именно окончательный файл: целостность ZIP, package ID, versionName и
versionCode, ABI, debug-флаг, подпись/сертификат, SHA-256 и применимый
runtime/DEX/native/assets-состав. Для стабильного выпуска debuggable выключен.
Неподписанный промежуточный файл, старый лог или JVM-тест не заменяют этот gate.
Для обновления сравни пакет/подписанта и рост versionCode; отдельно проверь
совместимость данных. Полные правила native/runtime проверки приведены ниже.

Вычисли SHA-256 именно финального APK и сформируй SHA256SUMS. Подготовь компактный
отчёт. Для стабильного выпуска создай update.json из этого же проверенного файла
и проверь совместимость со встроенным обновлятором, как описано в его разделе.

### Проверка сертификата release перед упаковкой

Release использует существующий `.signing/fork-debug.jks` через отдельную
`signingConfigs.release`, наследующую прежние ключ/alias/параметры доступа.
`scripts/build-local-arm64.sh` не вызывает генератор ключа и отказывает, если
keystore отсутствует. Задачи validateSigning/package/assemble/bundle release
зависят от обязательного `verifyReleaseSigner` без кешируемого результата.

Ожидаемый **публичный** SHA-256 сертификата закреплён в
[gradle/release-certificate.sha256](../../gradle/release-certificate.sha256).
[Проверяющий код](../../gradle/verify-release-signer.gradle) получает только
публичный certificate выбранного alias; отсутствие ключа/pin, неверный доступ
или несовпадение останавливают release. Пароли и private-key entries не выводятся
и не экспортируются. Сам signer штатно использует существующий ключ при подписи.
Не генерировать замену и не менять pin автоматически ради прохождения проверки.

Проверка до упаковки не заменяет `apksigner verify --print-certs` и сравнение
сертификата именно окончательного APK с прежним Termux Job’s. Совпадения package
ID недостаточно. Отладочные тесты и Lint не являются выпуском signed release.

### Проверка runtime-зависимостей (v1.3.3+)

Прохождение JVM-тестов не доказывает состав Android APK: варианты зависимостей
могут различаться. preBuild проверяет файловые API Guava в debug/release runtime.
ARM64 build запускает scripts/verify-apk-runtime.py на финальном APK. Не удаляйте
ошибку проверки добавлением в список исключений без определения происхождения
типа, его вызывающих путей и доступности на поддерживаемом Android.
Сверяйте определения DEX, а не только строки ссылок. Staging не должен содержать
удалённых Java-исходников. Изменение minSDK указывать в RU/EN metadata до установки.

## In-app updater (since v1.0.19)

Alongside APK and SHA256SUMS, upload **update.json** to each stable release.
Generate it from the final verified APK, not a preliminary build:

```sh
python3 scripts/create-update-manifest.py \
  --apk .verification/release-vVERSION/Termux-Jobs-vVERSION-arm64.apk \
  --aapt2 /path/to/existing/aapt2 \
  --notes docs/fork/UPDATE-NOTES-vVERSION.json \
  --output .verification/release-vVERSION/update.json
```

Notes contain `ru`/`en` change arrays and a required `compatibility` object with
`ru`/`en` arrays. The generator appends compatibility to highlights, up to 20 total
lines per language, so existing v1.0.19 clients display it before installation. Use the same
APK/hash/version as the release assets. Upload metadata before publishing the
release. Download all three assets back and verify consistency. The updater uses
GitHub's latest stable release, requires increasing versionCode and exact current
signer/package match, and never offers uninstall as an update workaround. Missing
metadata produces an explicit unsupported-release message. A successful source
build does not establish end-to-end Android installer or data-migration behavior.
Do not publish an artificial higher-version release solely to test the updater.

For every future stable release, explicitly document data compatibility in RU/EN
update highlights as well as release notes. Include any required clearing of
commands/presets, loss of data, incompatible formats or migrations and their
reasons **before** installation. If no reset is required, say that explicitly.
Keep the metadata schema readable by installed v1.0.19 clients. Never silently
reset user data or publish without the updater assets.

## Документация перед публикацией

Веди единый CHANGELOG.md, сохраняя старые записи. Обязательно проверить
и обновить по фактическому состоянию:

- `README.md`: только актуальная опубликованная стабильная версия, возможности,
  установка, ссылка на её APK, совместимость, действующие известные ограничения
  и ссылки на документацию, CHANGELOG и Releases. Историю старых релизов,
  rollback и приватных test-сборок храни в CHANGELOG, Releases и отчётах,
  не в README. Возраст обнаружения ограничения не означает его устранение:
  проверь актуальность и сохрани те ограничения, которые остаются.
- `CHANGELOG.md`: изменения относительно последнего опубликованного стабильного релиза.
- `docs/fork/RELEASE-<tag>.md`: самостоятельное описание нового релиза.
- `docs/fork/VALIDATION-vVERSION.md`: собственный отчёт каждого релиза с итоговым
  APK, размером, SHA-256, сертификатом, выполненными проверками и непроверенными
  сценариями. Release notes ссылаются на этот отчёт в теге своей версии.
  Общий `docs/fork/VALIDATION.md`, если используется, служит указателем на отчёты,
  а не смешивает результаты разных выпусков.
- `FORK.md`: версия и актуальные требования сборки.
- `docs/fork/USAGE.md`, `DESIGN.md`, `ARCHITECTURE.md`: изменившееся поведение,
  интерфейс, хранение и выполнение команд.
- `CONTINUE.md`: актуальный контекст продолжения работы.
- Шаблоны Issues и `CONTRIBUTING.md`: актуальные вопросы и ссылки.

Не переписывать историю прежних релизов как новые результаты. Старые отчёты
помечать историческими. Если документ не требует изменений, проверить его
соответствие релизу; бессодержательные правки не нужны.

### Формат публичного описания релиза

Пиши описание на английском: конкретными короткими пунктами о новых
возможностях, изменённом поведении и исправлениях. Объединяй связанные изменения
по пользовательским функциям. Используй следующий порядок:

1. В начале дай короткое описание главных изменений и прямую ссылку
   **Download APK** на подписанный release APK в assets этого релиза.
2. Опиши новые возможности, изменения поведения и исправления относительно
   последнего опубликованного стабильного релиза. Не перечисляй промежуточные test-сборки,
   их номера, отменённые эксперименты и дефекты, возникшие только при их разработке.
3. Затем укажи требования, совместимость обновления и важные ограничения.
   Не прячь условия установки, риски потери данных или существенные ограничения
   в технические подробности.
4. Подробности CI, исходные отказы, повторные проверки, коммиты, хеши, размеры
   и параметры инструментов помести в раскрываемый блок `<details>` с понятным
   `<summary>`. Внутри оставь ссылки на отчёты и соответствующие запуски.
   Сохраняй пустые строки между HTML-тегами и Markdown для корректного отображения.
5. Внутри технического блока явно раздели debug CI и проверки опубликованного
   подписанного release APK, а также локальные проверки и наблюдения на телефоне.
   Укажи пропущенные тесты отдельно; не считай их успешными. Сохраняй исходные
   неудачные результаты при добавлении новых успешных проверок.

Используй читаемые пробелы между словами, числами и единицами: например,
`proot-distro 5.9.0`, `NDK 22.1.7171670`, `32 MiB`, `40,452,595 bytes`,
`versionCode 1476`. Не склеивай версии, размеры и названия инструментов.
Последняя строка с указанием ИИ-помощника сохраняется после `</details>`.

В публикуемом release body используйте полные HTTPS-ссылки на документацию,
например https://github.com/HezeAI/termux-jobs/blob/vVERSION/docs/fork/BACKUP-RESTORE.md.
Относительный BACKUP-RESTORE.md из страницы releases/tag не ведёт в docs/fork.
Перед публикацией проверьте наличие файлов в соответствующем теге, после неё —
публичную доступность каждой ссылки и совпадение release body с подготовленным.
Для исправления только текста/ссылок редактируйте release notes и документацию,
не пересобирайте APK, не передвигайте опубликованный тег и не меняйте update.json.

Роль debug остаётся внутренней, как описано в разделе «Debug в CI и проверка
release»; этот формат не требует выдавать debug APK при каждом релизе.
Для уже опубликованной версии меняй только описание и относящуюся документацию:
не заменяй APK, `update.json`, тег или бинарные Components ради оформления.
Правило оформления само по себе не разрешает публикацию будущих релизов.
Подробные требования хранятся здесь; существующая ссылка из AGENTS.md остаётся
точкой входа, без дублирования этих правил.

## Git: commit, push и тег

1. До коммита проверь точный состав файлов и `git diff --check`: без секретов,
   личных данных, авторизации, приватных ключей, Alpha, личных подключений,
   рабочих журналов, локальных сред/инструментов, кешей, временных и тяжёлых
   промежуточных артефактов. Проверь ссылки.
2. Сохрани исходники, документацию, патчи и необходимые материалы сборки
   финальной версии. Включи новые нужные файлы, а не только изменённые ранее
   отслеживаемые. Локальный кеш не добавляй как исходники.
3. Создай релизный коммит и тег, соответствующие проверенному финальному APK.
   Сверь версии, значимые исходники, ресурсы, зависимости и входы сборки с коммитом.
4. При наличии разрешения отправь согласованную ветку разработки форка и тег
   на GitHub. Не используй force push и не перемещай опубликованные теги без
   отдельного разрешения.
5. Проверь доступность ветки, коммита и тега, их соответствие и ссылки на нужную
   версию. Документация релиза должна вести на исходники именно этой версии.

Push исходников/документации без APK допускается отдельным действием в пределах
авторизации. Он не означает публикацию стабильного релиза и не должен
самостоятельно переключать канал обновления.

## Публикация

До публикации подготовь конкретный результат для просмотра: название, release
notes, состав исходников, список файлов и результаты проверок. Публикуй только
в пределах разрешения на текущий выпуск; уже данное разрешение повторно не
запрашивай. Установка APK и остановка рабочих сессий автоматически не разрешаются
публикацией. Правила документа не дают разрешения на будущие публикации.

Опубликуй APK, SHA256SUMS, update.json и описание. Метаданные загрузи до
публикации. Для обычного стабильного выпуска проверь draft=false/prerelease=false
и правильный стабильный канал. Один push не обновляет его автоматически.
Не публикуй искусственный релиз с повышенной версией только ради теста обновлятора.

## Проверка публичного скачивания и итог

После публикации скачай публичные APK, SHA256SUMS и update.json обратно и проверь
совпадение SHA-256, версий, package/signer и метаданных обновления. Проверь
публичную доступность ссылок описания, ветки и тега, состав файлов и метаданные
релиза. Сверь фактический `tag_name` ответа GitHub с ожидаемым тегом и его коммитом;
проверь versionName/versionCode APK, адреса ресурсов, размер и SHA-256 против
SHA256SUMS и update.json. Проверь, что встроенный обновлятор принимает опубликованные
метаданные по своим правилам версии, package ID и сертификата. Ответ API об успешном
изменении релиза не заменяет эту сверку и фактическое публичное скачивание.
Для добавленных Components выполни также проверки их публичных файлов
и штатного загрузчика по разделу лицензий.

После публикации проверь README основной ветки, указанной GitHub как default_branch,
и его отображение на главной странице репозитория. Сверь актуальный стабильный релиз,
ссылку APK, ограничения и ссылки на отчёты. Проверки только README релизного тега
недостаточно. При отдельном обновлении README сохрани более свежие изменения основной
ветки; не переноси функциональные изменения рабочей ветки ради документации.

В итоговом отчёте укажи ветку, хеш опубликованного коммита, тег, ссылку на релиз
и результаты проверок. Раздели локальные/CI и debug/release результаты;
не переписывай первоначальный неудачный CI-run как успешный. Обнови контекст
продолжения и оставшиеся проверки. Непроверенные и исключённые области аудита
сохраняются явно.
